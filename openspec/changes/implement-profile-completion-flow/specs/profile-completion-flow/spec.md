## ADDED Requirements

### Requirement: Защищенный маршрут заполнения профиля
Система SHALL предоставлять отдельный защищенный frontend route для процесса заполнения профиля после авторизации.

#### Scenario: Авторизованный пользователь открывает маршрут флоу
- **WHEN** пользователь с активной сессией открывает route заполнения профиля
- **THEN** система MUST отобразить экран процесса заполнения профиля внутри существующих `AppProviders` и `AuthGuard`

#### Scenario: Глобальный redirect еще не подключен
- **WHEN** пользователь успешно авторизуется
- **THEN** система MUST NOT добавлять автоматический redirect на onboarding без отдельного onboarding status

### Requirement: Общий экранный шаблон флоу
Система SHALL использовать общий шаблон экрана для всех шагов заполнения профиля.

#### Scenario: Отображается любой шаг флоу
- **WHEN** пользователь находится на любом шаге заполнения профиля
- **THEN** система MUST показывать общий layout с логотипом, progress/stepper зоной, контентной областью шага и основной нижней CTA-кнопкой

#### Scenario: Шаг меняется
- **WHEN** пользователь переходит между шагами
- **THEN** система MUST переиспользовать тот же экранный шаблон и заменять только данные и контент текущего шага

#### Scenario: Верхний stepper используется для навигации
- **WHEN** пользователь выбирает доступный шаг в верхнем stepper
- **THEN** система MUST перейти к выбранному шагу без потери уже введенных данных текущей сессии флоу

### Requirement: Декларативное переключение шагов
Система SHALL управлять шагами через единый декларативный список конфигураций.

#### Scenario: Пользователь нажимает основную кнопку доступного шага
- **WHEN** текущий шаг валиден и пользователь нажимает основную CTA-кнопку
- **THEN** система MUST перейти к следующему шагу согласно декларативному порядку шагов

#### Scenario: Пользователь возвращается назад
- **WHEN** пользователь использует back navigation внутри флоу
- **THEN** система MUST перейти к предыдущему шагу без потери уже введенных данных текущей сессии флоу

#### Scenario: Шаг невалиден
- **WHEN** текущий шаг не удовлетворяет своей проверке доступности продолжения
- **THEN** система MUST не позволить перейти дальше через основную CTA-кнопку или верхний stepper

### Requirement: Все уникальные шаги из Figma входят во флоу
Система SHALL включать все уникальные шаги из Figma node `2031:5312`, трактуя дублирующие фреймы как состояния тех же шагов.

#### Scenario: Разработчик реализует шаги по Figma
- **WHEN** разработчик сопоставляет Figma node `2031:5312` с реализацией
- **THEN** система MUST покрыть уникальные шаги интро/анонимности, nickname, профессиональных и локационных выборов, уровня/стажа, зарплаты/бонуса, навыков и финальной сверки

#### Scenario: Figma содержит несколько фреймов одного шага
- **WHEN** в Figma есть несколько фреймов одного шага с разными состояниями
- **THEN** система MUST реализовать их как состояния одного шага, например empty, filled, error, optional field hidden/shown или selected values

### Requirement: Централизованное состояние и DTO-маппинг
Система SHALL хранить состояние заполнения профиля централизованно и преобразовывать его в `OnboardingDto` перед отправкой.

#### Scenario: Пользователь меняет данные на шаге
- **WHEN** пользователь вводит или выбирает значение на любом шаге
- **THEN** система MUST обновить единое состояние флоу без немедленной отправки onboarding DTO

#### Scenario: Пользователь доходит до финальной отправки
- **WHEN** пользователь подтверждает финальный шаг
- **THEN** система MUST построить `OnboardingDto` из состояния флоу, преобразовать числовые поля и исключить выключенные optional fields

#### Scenario: Страница обновляется
- **WHEN** пользователь обновляет вкладку или заново открывает route флоу
- **THEN** система MUST NOT восстанавливать draft из localStorage или sessionStorage

### Requirement: Проверка nickname через моковый API-call
Система SHALL проверять доступность nickname через моковый API-call до появления реального backend endpoint.

#### Scenario: Nickname доступен
- **WHEN** пользователь вводит валидный nickname и продолжает шаг nickname
- **THEN** система MUST вызвать моковую проверку nickname и разрешить переход дальше при доступном имени

#### Scenario: Nickname занят
- **WHEN** моковая проверка возвращает состояние занятого nickname
- **THEN** система MUST остаться на шаге nickname и показать ошибочное состояние согласно Figma-макету занятого nickname

### Requirement: Данные каталогов и поиска нормализуются для UI
Система SHALL получать данные каталогов и поиска через сгенерированный API-клиент и передавать UI-компонентам нормализованные options.

#### Scenario: Временные mock adapters возвращают DTO-like данные
- **WHEN** шаг запрашивает город, грейд, профессию, компанию, формат работы, навык или поисковые результаты во время разработки
- **THEN** система MUST вернуть mock-данные, совместимые с generated DTO shape, и код MUST содержать TODO на замену реальным API вызовом

#### Scenario: Шагу нужны популярные варианты
- **WHEN** шагу нужны популярные профессии, компании или города
- **THEN** система MUST использовать соответствующие методы `getTopProfessions`, `getTopCompanies` или `getTopCities` и нормализовать ответ в options для UI-компонентов

#### Scenario: Шагу нужен поиск
- **WHEN** пользователь вводит поисковый запрос для компании, навыка, профессии, страны или города
- **THEN** система MUST использовать generated `search` API с соответствующим типом и отображать нормализованные результаты в компоненте шага

#### Scenario: Шагу нужны enum options
- **WHEN** шагу нужны форматы работы или уровни seniority
- **THEN** система MUST использовать generated catalog options API или локальный fallback, совместимый с enum-значениями `OnboardingDto`

### Requirement: Отправка onboarding данных
Система SHALL отправлять заполненный профиль через `api.saveOnboarding` из существующего API wrapper.

#### Scenario: Финальная отправка успешна
- **WHEN** пользователь подтверждает финальный шаг с валидным DTO
- **THEN** система MUST вызвать `api.saveOnboarding` с построенным `OnboardingDto` и обработать успешное завершение флоу

#### Scenario: Финальная отправка завершилась ошибкой
- **WHEN** `api.saveOnboarding` возвращает ошибку
- **THEN** система MUST показать ошибку без сброса введенных пользователем данных текущей сессии флоу
