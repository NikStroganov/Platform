## Context

Frontend уже использует Next.js App Router, React, MUI v9, общий `ThemeProvider`, `AuthGuard` и API wrapper `frontend/lib/api/client.ts`. После успешной авторизации пользователь попадает в защищенную часть приложения, но полноценного onboarding/profile completion флоу еще нет.

Базовые UI-компоненты для этого сценария уже выделены capability `design-system-components`: `AppStepper`, `AppButton`, `FieldInput`, `GradeSelect`, `SwitchButtons`, `CompanyButtons`, `CityButtons`, `SpecialityButtons`, `ToggleWithLabel`, `ChipInput` и связанные компоненты. Figma node `2031:5312` задает общий визуальный флоу: интро/анонимность, ввод никнейма, выбор профессии/компании/города/формата, грейд и стаж, зарплата и бонус, навыки, финальная сверка.

Backend-контракт доступен через сгенерированный API. Финальная отправка данных выполняется методом `api.saveOnboarding(data)`, где `data` соответствует `OnboardingDto`: `nickname`, `companyId`, `countryId`, `cityId`, `workFormat`, `professionId`, `seniorityLevel`, `companyGrade`, `workExperienceYears`, `salary`, `bonus`, `currency`.

## Goals / Non-Goals

**Goals:**

- Создать общий экранный каркас флоу, который переиспользуется всеми шагами: логотип, stepper/progress, контентная область, нижняя CTA-кнопка, back/next navigation.
- Ввести единый механизм переключения шагов и накопления данных onboarding-формы.
- Подготовить архитектуру, в которой каждый шаг можно реализовывать отдельно по своему Figma-макету без переписывания общего шаблона.
- Заложить моковый API-call для проверки занятости nickname до появления реального endpoint.
- Использовать существующие компоненты дизайн-системы и сгенерированный API-клиент.
- Держать DTO-маппинг в одном месте, чтобы UI-состояние шагов не расползалось по компонентам.

**Non-Goals:**

- Не реализовывать все шаги полностью в первом implementation-этапе.
- Не менять backend API, сгенерированные файлы API вручную или схему `OnboardingDto`.
- Не создавать новую UI-библиотеку или дубли компонентов, уже покрытых `design-system-components`.
- Не добавлять сохранение draft при уходе со страницы или обновлении вкладки.
- Не реализовывать глобальный redirect на onboarding до появления отдельного onboarding status.

## Decisions

### 1. Флоу размещается как отдельный protected route

Создать отдельную страницу, например `frontend/app/onboarding/page.tsx` или близкий по смыслу route. Route остается под существующим `AuthGuard`, потому что onboarding заполняется после авторизации и использует авторизованный API wrapper.

Альтернатива: встроить флоу в текущий `/` home screen. Отказ: домашняя страница уже содержит временный тестовый UI, а onboarding имеет собственную последовательность экранов и должен быть легко перенаправляемым после auth.

### 2. Общий layout отделяется от конкретных шагов

В feature-модуле, например `frontend/features/profile-completion`, выделить:

- `ProfileCompletionPage` или `ProfileCompletionFlow` как контейнер состояния;
- `ProfileCompletionLayout` как общий экранный шаблон;
- `steps/*` как компоненты отдельных шагов;
- `model/*` как типы, список шагов, reducer/hook и DTO-маппинг;
- `api/*` как тонкие функции получения catalog/search/top-list данных, если они нужны шагу.

`ProfileCompletionLayout` получает конфигурацию текущего шага: индекс, количество шагов, title, description, content, primary action, back action, stepper action, disabled/loading/error states. Конкретный шаг рендерит только свою форму и сообщает изменения наверх.

Альтернатива: держать весь JSX шагов в одном большом page component. Отказ: поэтапная реализация по отдельным макетам быстро превратит страницу в хрупкий компонент, где трудно менять порядок, валидацию и DTO-маппинг.

### 3. State флоу хранится централизованно и маппится в `OnboardingDto`

Ввести внутренний тип состояния, близкий к UI, но совместимый с backend:

- строковые поля ввода: `nickname`, `customCompanyGrade`, `workExperienceYears`, `salary`, `bonus`;
- выбранные id: `companyId`, `countryId`, `cityId`, `professionId`;
- enum-значения: `workFormat`, `seniorityLevel`, `currency`;
- UI toggles: `hasCompanyGrade`, `hasBonus`;
- дополнительные UI-данные для summary: label/name/logo/backgroundColor, если они нужны для финальной сверки.

Отдельная функция `buildOnboardingDto(state): OnboardingDto` отвечает за преобразование строк в числа, исключение выключенных optional fields и проверку обязательных id. Это позволяет шагам работать с удобным UI-state, не смешивая JSX с backend DTO.

Альтернатива: хранить состояние сразу как `Partial<OnboardingDto>`. Отказ: UI имеет дополнительные toggles и display labels, а числовые поля удобнее валидировать как строки до отправки.

### 4. Переключение шагов управляется декларативным списком

Список шагов задается массивом конфигураций:

- `id`;
- `progressVisible`;
- `title`/`description`;
- `render`;
- `canContinue(state)`;
- `onBeforeNext` для асинхронной проверки или сохранения, если потребуется;
- `mapFigmaNode` или комментарий со ссылкой на конкретный Figma sub-frame для последующей реализации.

Первый implementation-этап может включать placeholder content для еще не реализованных шагов, но navigation, интерактивный верхний stepper, кнопки и state transitions должны работать сразу. При клике на stepper флоу может переходить к уже доступному шагу; переход вперед через stepper должен проходить те же проверки доступности, что и основная CTA-навигация.

Альтернатива: переключать шаги через `switch(currentStep)` прямо в компоненте. Отказ: конфигурация шагов будет хуже расширяться и труднее проверяться против Figma.

### 5. Валидация делится на локальную и финальную

Каждый шаг определяет минимальные условия для перехода дальше: непустой nickname, выбранная профессия, выбранная компания, корректный стаж, зарплата в допустимом диапазоне и т.д. Финальная отправка дополнительно валидирует DTO перед `api.saveOnboarding`.

Если backend вернет ошибку, контейнер флоу показывает ошибку на текущем или финальном шаге без сброса введенных данных.

Альтернатива: валидировать только перед финальной отправкой. Отказ: пользователь сможет пройти несколько экранов с незаполненными обязательными данными и получит позднюю, менее понятную ошибку.

### 6. Data fetching остается рядом с шагами, но через тонкие adapter-функции

Для шагов выбора использовать сгенерированные методы:

- `getTopProfessions`, `getTopCompanies`, `getTopCities` для популярных вариантов;
- `getWorkFormats`, `getSeniorityLevels` для catalog options;
- `search` с типами `COMPANY`, `SKILL`, `PROFESSION`, `COUNTRY`, `CITY` для поисковых списков.

Сами компоненты дизайн-системы получают уже нормализованные options: `{ value, label, ...visual }`. Это удерживает UI-kit независимым от backend DTO.

Альтернатива: передавать raw DTO прямо в UI-компоненты. Отказ: это свяжет дизайн-систему с конкретным API и усложнит Storybook/тестовые данные.

## Risks / Trade-offs

- [Risk] Порядок шагов в Figma node `2031:5312` может быть уточнен по отдельным макетам. -> Mitigation: держать порядок в одном декларативном массиве и добавлять `id` шагов, чтобы перестановка не ломала state.
- [Risk] Часть данных для summary нужна только для отображения, но отсутствует в `OnboardingDto`. -> Mitigation: хранить display metadata отдельно от DTO и не отправлять ее в `saveOnboarding`.
- [Risk] Сгенерированный API может измениться после обновления OpenAPI. -> Mitigation: не импортировать типы из внутренних implementation-файлов, использовать публичные `Api.ts`/`data-contracts.ts` и держать adapter-функции узкими.
- [Risk] Асинхронные поисковые запросы могут давать гонки при быстром вводе. -> Mitigation: на уровне шагов использовать debounce/cancellation или проверку актуальности query перед применением результата.
- [Risk] Первый этап с placeholder-шагами может выглядеть как неполная реализация. -> Mitigation: задачи должны явно разделять "каркас и механизм" от "наполнение шагов по макетам", а placeholders не должны попадать в финальный completed-flow.
- [Risk] Onboarding route может конфликтовать с auth redirect после логина. -> Mitigation: на этапе реализации согласовать минимальное правило перехода: после успешной авторизации вести на onboarding, пока нет признака завершенного профиля.

## Migration Plan

1. Добавить route и feature-модуль profile completion без удаления текущего home/test UI.
2. Реализовать общий layout, stepper, navigation и state-механизм с безопасными placeholder-шагами.
3. Подключать реальные шаги по одному макету, заменяя placeholders и добавляя adapter-функции для нужных API-данных.
4. На финальном шаге подключить `api.saveOnboarding` и переход после успешной отправки.
5. После проверки полного флоу убрать или заменить временный home/test UI, если он больше не нужен.

Rollback: route можно не включать в post-auth navigation и оставить пользователя на текущей `/` странице; feature-модуль изолирован и не должен ломать auth/API wrapper.

## Resolved Decisions

- Признак завершенного onboarding будет отдельным status; глобальный redirect на onboarding в этом change не реализуется.
- Проверка nickname должна быть заложена как моковый API-call до появления реального endpoint.
- Ручки каталогов и поиска для городов, грейдов/seniority, профессий, компаний, формата работы и навыков временно реализуются mock adapters с TODO; они возвращают DTO-like данные, совместимые с generated API types.
- Draft заполнения профиля не сохраняется при уходе со страницы или обновлении вкладки.
- Все уникальные шаги из Figma node `2031:5312` входят во флоу; дублирующие фреймы являются состояниями тех же шагов.
