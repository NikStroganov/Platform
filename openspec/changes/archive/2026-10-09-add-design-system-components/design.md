## Context

Проект уже использует Next.js, React, MUI v9, `ThemeProvider` и Storybook. В `frontend/components/ui` есть базовые компоненты (`AppButton`, `AppTextField`, `SegmentedTabs`, `OtpInput`, `DottedBorderInput`), а общие визуальные настройки частично вынесены в `frontend/lib/theme.ts`.

Новый набор компонентов должен продолжить этот подход: максимально опираться на MUI, не вводить параллельную UI-библиотеку и не дублировать поведение, которое уже есть в MUI. Документы OpenSpec для этого change ведутся на русском языке.

Figma-фрейм `1970-5263` является обязательным источником истины для состава компонентов, вариантов, визуальных состояний, размеров, spacing, цветов и примеров, которые попадут в Storybook.

## Goals / Non-Goals

**Goals:**

- Реализовать Stepper, Search input, Company buttons, Switch buttons, Speciality buttons, Grade select, Toggle with label, Chip, Chip input и Chip suggestion как переиспользуемые UI-компоненты.
- Сверять реализацию и Storybook-документацию с Figma-макетами до завершения задач.
- Максимально использовать npm-пакет `@mui/material`: базовые primitives, состояния, keyboard/focus-поведение, accessibility-атрибуты и theme overrides.
- Добавить внешний вид Button как стиль/вариант к уже существующему `AppButton` и MUI `MuiButton`, а не создавать конкурирующий компонент кнопки.
- Для компонентов с кастомными цветами принимать цвета пропсами в формате hex-строк.
- Для компонентов с изображениями принимать изображения пропсами как URL-строки.
- Документировать компоненты в Storybook с основными вариантами, состояниями и интерактивными примерами.

**Non-Goals:**

- Не менять продуктовые сценарии и backend API.
- Не добавлять новую UI-библиотеку поверх MUI.
- Не хранить изображения этих компонентов как локальные обязательные ассеты, если они могут передаваться URL.
- Не создавать отдельную Button-абстракцию, которая обходит существующий `AppButton`.

## Decisions

### 1. MUI как основной слой реализации

Компоненты проектируются поверх MUI primitives:

- Stepper: `Stepper`, `Step`, `StepLabel` или легкая композиция MUI layout primitives, если макет требует кастомной геометрии.
- Search input: существующий `AppTextField` или MUI `TextField` с `InputAdornment`.
- Grade select: MUI `Select`, `MenuItem`, `FormControl` или `Autocomplete`, если по макету нужен поиск/подсказки.
- Toggle with label: MUI `Switch` плюс `FormControlLabel`.
- Chip, Chip input, Chip suggestion: MUI `Chip`, `Autocomplete`, `TextField`.
- Company, Switch и Speciality buttons: `ButtonBase`, `ToggleButton`, `ToggleButtonGroup` или существующий паттерн `SegmentedTabs`, в зависимости от поведения выбора.

Альтернатива: реализовать все на `div`/`button` вручную. Отказ: это увеличит объем accessibility, keyboard navigation и state management, которые MUI уже закрывает.


### 2. Figma как источник истины для визуального результата

Перед реализацией каждого компонента нужно сверить его варианты и состояния с Figma-фреймом `1970-5263`. Если MUI primitive дает другое визуальное поведение по умолчанию, внешний вид доводится до макета через theme, `styled`, `sx` или wrapper, сохраняя MUI как основу поведения.

Если в Figma для компонента не указано отдельное состояние, например disabled, hover, focus, error или empty, это состояние нужно спроектировать по общему стилю текущей дизайн-системы и существующих MUI/theme-паттернов, не нарушая визуальную логику макета.
Альтернатива: ориентироваться только на существующие компоненты и приблизительные токены. Отказ: это может привести к расхождению с утвержденным дизайном и к Storybook, который не отражает макет.
### 3. Button расширяется через существующий AppButton

Новый визуальный вариант кнопки добавляется как стиль существующего `AppButton` и/или как MUI theme variant в `MuiButton`. `AppButton` остается единой входной точкой для проектных кнопок и продолжает наследовать `ButtonProps`.

Если макет требует новый вид, предпочтительный путь:

- добавить именованный prop или MUI-compatible variant/style mapping в `AppButton`;
- вынести повторяемые токены в `theme.ts`;
- обновить `AppButton.stories.tsx`, чтобы показать новый стиль и состояния.

Альтернатива: создать новый компонент `Button`. Отказ: в проекте уже есть `AppButton`, и второй компонент с той же ролью создаст расхождение API и стилей.

### 4. Кастомные цвета передаются как hex-пропсы

Компоненты, которым нужны динамические цвета из данных или макета, принимают их явными prop-полями с типом `string` и семантическими именами, например `colorHex`, `backgroundHex`, `selectedColorHex`, `accentColorHex`.

Правила:

- ожидаемый формат значения: hex (`#RGB`, `#RRGGBB`, при необходимости `#RRGGBBAA`);
- дефолтные цвета берутся из theme tokens;
- runtime-валидация может нормализовать некорректные значения к дефолту, если компонент используется с внешними данными;
- MUI `sx` остается escape hatch, но не заменяет документированные color props.

Альтернатива: принимать любые CSS color-строки. Отказ: это усложняет контроль визуальной системы и может привести к несовместимым форматам.

### 5. Изображения передаются как URL

Компоненты с изображениями, например company buttons, принимают `imageUrl`, `logoUrl`, `iconUrl` или аналогичный prop как строку URL. Компонент не должен требовать локального импорта изображения.

Правила:

- URL передается снаружи;
- обязательны `alt` или доступная текстовая альтернатива;
- компонент должен корректно работать без изображения, если это допустимо по макету;
- размеры и object-fit задаются компонентом, чтобы URL-картинка не ломала layout.

Альтернатива: импортировать ассеты внутрь компонента. Отказ: это привяжет UI-kit к конкретным данным и ухудшит переиспользование.

### 6. Storybook как контракт визуального поведения

Для каждого компонента создается story рядом с текущими `frontend/stories/*.stories.tsx`. Stories должны показывать:

- базовый вариант;
- selected/active состояние, если есть выбор;
- disabled состояние, если применимо;
- hover/focus/interaction через controls или play-friendly examples, где это уместно;
- примеры с кастомными hex-цветами;
- примеры с URL-изображениями для компонентов, которым нужны картинки.

Альтернатива: документировать только дефолтный вид. Отказ: дальнейшая разработка будет хуже видеть границы API и состояния компонента.

## Risks / Trade-offs

- [Risk] MUI-компоненты могут не совпасть с Figma pixel-perfect по отдельным деталям. -> Mitigation: использовать MUI как поведенческую основу, а геометрию/цвета/spacing доводить через `styled`, `sx`, `theme.components` и локальные wrapper-компоненты.
- [Risk] Реализация может уйти от Figma при опоре на дефолты MUI. -> Mitigation: проверять каждый компонент и Storybook story против Figma-фрейма `1970-5263` перед закрытием задачи.
- [Risk] Hex-пропсы могут начать дублировать theme tokens. -> Mitigation: hex-пропсы использовать только для реально динамических цветов; статичные проектные цвета держать в `theme.ts`.
- [Risk] URL-картинки могут иметь непредсказуемые размеры или быть недоступны. -> Mitigation: задавать фиксированные constraints, fallback-состояние и доступный текст.
- [Risk] Добавление многих компонентов сразу может размыть API. -> Mitigation: держать props минимальными, повторять MUI naming там, где это естественно, и фиксировать варианты в Storybook.
- [Risk] Новый стиль Button может конфликтовать с текущими overrides `MuiButton`. -> Mitigation: оформлять новый стиль как явный variant/prop и проверять существующие stories `AppButton`.




### 7. ChipInput использует единый active/overflow режим

ChipInput хранит выбранные значения во внешнем value и синхронизирует верхние chips с результатами active search. При переполнении и область chips, и список результатов используют нативную прокрутку браузера.

Правила:

- scrollbar стилизуется стандартными CSS-свойствами scrollbar-width, scrollbar-color и WebKit-псевдоэлементами;
- кастомные DOM-контролы и кнопки прокрутки не используются;
- список результатов скрывается при потере фокуса за пределами компонента;
- Storybook overflow-история использует один набор options и value, чтобы демонстрировать синхронизацию в обоих направлениях.

Альтернатива: отдельные режимы и собственный контрол scrollbar. Отказ: это дублирует логику, ухудшает нативное взаимодействие с колесом/тачпадом и не отражает единый публичный API компонента.
